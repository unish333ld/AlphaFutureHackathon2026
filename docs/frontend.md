# Frontend

Новый договорный путь (API 1.3): PDF → явное ознакомление → серверный демо-код → подпись → ожидание → выдача специалистом. В `.env` нужны `DEMO_MODE=true` и `DEMO_SIGNATURE_ENABLED=true`; после изменений пересобрать frontend **и** backend прежнего Compose project. Реальные SMS и модель не нужны. Подробности, схемы и fallback без PDF-viewer: [agreements.md](agreements.md); проверки: [qa-product-research.md](qa-product-research.md).

Рабочий React-интерфейс в `frontend/`, без runtime-моков API. Исходный контракт 1.1.0 совпадал со снимком навыка `alfa-credit-frontend`; затем 1.2.0 добавил стоимость, сравнение предложений, readiness и источники каталога. Актуальный `docs/openapi.yaml` — **1.3.0**, с PDF и кодовым подтверждением. [Продуктовые изменения](product-research.md), [договорный протокол](agreements.md). Просмотрены все девять исходных PNG. Сохранены светлый фон, белые панели, красные действия, двухколоночная клиентская форма и банковская очередь/карточка. Фиктивные Grade, SLA, приоритет, ручной выбор решения и банковская ИИ-сводка не перенесены.

## Запуск

Из корня, после заполнения `.env` по README:

```sh
docker compose up --build -d --wait --wait-timeout 180
```

Открыть http://localhost:8080. Логины `client`, `specialist`, `accountant`, `outsider`; пароль — ваш `DEMO_PASSWORD`. Роль не выбирается в API входа. Кнопки «Клиент»/«Специалист» только заполняют логин. Swagger с той же сессией — `/api/docs/`, отдельный служебный HTML-вход — `/api/session/login/`.

Если порты заняты: `WEB_PORT=18000 FRONTEND_PORT=18080 docker compose -p credit-demo up --build -d --wait --wait-timeout 180`. Для существующего проекта Compose используйте его прежнее имя, чтобы сохранить подключение к той же БД. Не запускайте тесты на пользовательской демо-базе.

Для разработки нужен Node >=22.12 (проверялся Node24):

```sh
cd frontend
npm ci
cp .env.example .env.local
# BACKEND_URL=http://127.0.0.1:8000 — укажите реальный порт своего backend
npm run dev
```

Vite: http://127.0.0.1:5173. Все браузерные запросы идут на относительный `/api/v1/`; Vite proxy / Nginx обеспечивают один origin. `BACKEND_URL` — server-only настройка Vite. `VITE_AI_ASSISTANT_ENABLED=false` — публичный compile-time флаг, в Docker передаётся build-аргументом; после изменения требуется пересборка frontend. Секреты в `VITE_*` запрещены. При false нет ни кнопки, ни панели помощника. При true клиенту доступно плавающее окно Савелия с историей, серверными фактами и предложением черновика. Для ответа модели также нужен `AI_ENABLED=true` и настроенный на сервере OpenAI-совместимый LLM endpoint. При недоступности модели основная заявка работает без неё.

### Если кнопка Савелия не отображается в Docker

1. Войдите как клиент: на странице входа и в кабинете специалиста кнопка намеренно отсутствует.
2. В корневом `.env` задайте `VITE_AI_ASSISTANT_ENABLED=true`. Файл `frontend/.env.local` нужен для Vite dev, но исключён из Docker build context. `AI_ENABLED=true` на backend само по себе не показывает кнопку.
3. Пересоберите и пересоздайте frontend **того же Compose-проекта**, не затрагивая БД и backend:

   ```sh
   docker compose up --build --no-deps -d --wait --wait-timeout 120 frontend
   ```

   Если проект запускался с `-p`, используйте то же имя и прежние `FRONTEND_PORT`/`WEB_PORT`. `docker compose restart frontend` не меняет скомпилированный флаг. После пересборки обновите страницу браузера.
4. Проверьте контейнеры командой `docker compose ps` и `/api/v1/health/` через frontend origin. Для кнопки и открытия окна модель не требуется; для ответов отдельно нужны серверный `AI_ENABLED=true`, доступный LLM endpoint и установленная модель.
5. Для проверки кнопки, клавиатуры и открытия окна **без запроса к модели** выполните из `frontend/`:

   ```sh
   E2E_BASE_URL=http://127.0.0.1:8080 E2E_ASSISTANT_ENABLED=true npx playwright test tests/e2e/assistant.spec.ts --project=chromium --grep @assistant-ui --trace=off
   ```

   Тест использует `DEMO_PASSWORD` из окружения или корневого `.env`. Если запущенный backend использует старую конфигурацию, его демо-пароль может отличаться. Не сбрасывайте пароли существующих пользователей только ради теста. В Git Bash для Docker exec с абсолютными Linux-путями добавляйте `MSYS_NO_PATHCONV=1`, чтобы `/app/...` не превратился в Windows-путь.

Савелий открывается правой панелью шириной 440 px, на широком экране не перекрывает форму, на узком — занимает доступную область с клавиатурным focus trap и Escape. История находится на отдельном экране панели, текущая компания и номер заявки указаны явно. Готовые вопросы отправляются кнопкой. Смена маршрута сбрасывает контекст старой заявки. Для отправки используется текущий `expected_version`; при 409 история перечитывается без автоматического повтора. `suggested_draft` сначала показывает «было → станет» и переносится в обычную форму только после подтверждения; изменившаяся форма не перезаписывается. Перенос хранится только в памяти React. Ключ модели не передаётся браузеру. Контракт, retention и настройки: [assistant.md](assistant.md).

## Экраны и маршруты

| Экран | Маршрут | Данные и действия |
|---|---|---|
| Вход | `/login` | CSRF → session login → новый CSRF → me |
| Главная компании | `/app` | Доступные компании, продукты, последние заявки |
| Заявки и кредиты | `/app/loans` | Серверная пагинация/статус, пустое состояние |
| Новая заявка | `/app/loans/new` | Продукт, сумма/срок/цель, показатели, серверный калькулятор, проверка, отправка/черновик |
| Черновик/ответ/пересмотр | `/app/loans/:id/edit` | `mode=answer` / `mode=revise`, новая ревизия, 409 без потери ввода |
| Подтверждение получения | `/app/loans/:id/submitted` | Фактические номер/ревизия/статус, без обещания одобрения |
| Клиентская карточка | `/app/loans/:id` | История, проверки, решение/условия/график, принятие/отклонение, договор/условная подпись, результат выдачи |
| Очередь банка | `/staff` | Пагинация25, поиск, статус/риск, все/свободные/мои, сортировка, исполнители |
| Карточка банка | `/staff/applications/:id` | Компания/показатели, проверки/факторы, история, claim/release, уточнение, retry, серверное решение, выдача |

Список клиента остаётся списком всех доступных пользователю компаний. Переключатель компании на главной выбирает компанию **для новой заявки**, а не имитирует серверный фильтр. Суммы/сроки клиентского списка догружаются только для видимой страницы с лимитом четыре параллельных detail-запроса. Банковская очередь использует компактный специализированный ответ, без detail-запросов каждой строки.

## Безопасность и конкуренция

- Django HttpOnly sessions, `credentials: include`, CSRF до входа и ротация после входа. JWT нет. На 403 проверяется me; истёкшая сессия запрашивает повторный вход, не уничтожая ввод той же учётной записи.
- Логин и пароль — контролируемые поля Core Components; поддерживаются вставка, менеджер паролей, Enter и показ/скрытие пароля. При ошибке пароль очищается полностью; логин сохраняется. Пароль не обрезается и не нормализуется ни клиентом, ни сервером. Кнопки демо-профилей выбирают только логин: нужен фактический пароль из настроек окружения.
- Во время login/logout фоновая проверка сессии не запускается; ответы предыдущей auth-операции не меняют нового пользователя. При фоновом сбое чтения карточки/черновика сохраняются уже загруженная форма и несохранённый ввод. Ошибка обновления показана отдельно; неуспешный GET не считается свежим подтверждением доступности кредитного действия.
- Query keys включают пользователя, роль и область компании; смена пользователя/выход отменяет запросы, очищает кеш и намерения выдачи. Другие вкладки уведомляются BroadcastChannel. На сервере повторно проверяются все права и изоляция компаний.
- Действия берутся из `available_actions` по allowlist; учитываются allowed/reason_code/target_id. Клиент не выполняет выдачу и не задаёт банковские поля. Специалист не выбирает результат, сумму или ставку вручную.
- Деньги передаются десятичными строками, нормализация — BigInt, окончательный расчёт — сервер. Текущее состояние выбирается по current_revision_id, оценки/решения проверяются по идентификаторам, не порядку массива.
- Подтверждения используют актуальную версию и прочитанный hash договора. После sign/disburse перечитывается карточка. На 409 — перечитывание и проверка человеком, без автоповтора POST.
- После успешного sign сбой обновления карточки не стирает подтверждение: остаётся сообщение «Сервер подтвердил подпись», повторное подписание скрыто. Восстановление копии PDF не подписывает договор заново. От повторной отправки выдачи и генерации документа защищают синхронные блокировки, а не только loading-состояние кнопки.
- Перед выдачей UUID намерения сохраняется в sessionStorage с user/agreement. Финансовые payload туда не пишутся. Потеря ответа → сверка карточки; если результата нет, явный повтор с прежним ключом. При запрете storage выдача не отправляется.
- Истечение срока не выставляется локальным таймером. После чтения карточки очередь инвалидируется. «Время в состоянии» — фактическое, не SLA банка.

## Проверки

```sh
cd frontend
npm run api:generate
npm run typecheck
npm run test
npm run build
npm run test:smoke # основной frontend8080, VITE_AI_ASSISTANT_ENABLED=false
npx playwright install chromium firefox webkit
E2E_BASE_URL=http://127.0.0.1:18080 npm run test:e2e
```

Новые проверки входа намеренно создают настоящие сессии, включая неверный пароль. При многократных серийных прогонах одного IP можно достичь реального лимита login и получить 429: соблюдайте Retry-After, не отключайте throttle. Для повторной межбраузерной регрессии запускайте `npx playwright test --project=chromium` (затем firefox/webkit) отдельно с паузой не менее 60 секунд между движками. Полный один прогон также зависит от состояния окна лимита предыдущих запусков.

E2E изменяют только синтетические данные. Поднимите отдельный проект `alfa-credit-ui-e2e` с WEB_PORT=18002, FRONTEND_PORT=18080, VITE_AI_ASSISTANT_ENABLED=true. Для гонки нужен второй специалист (без superuser), создаваемый в его БД:

```sh
WEB_PORT=18002 FRONTEND_PORT=18080 VITE_AI_ASSISTANT_ENABLED=true docker compose -p alfa-credit-ui-e2e up --build -d --wait --wait-timeout 180
docker compose -p alfa-credit-ui-e2e exec -T web python manage.py shell -c 'import os; from accounts.models import User; u, _ = User.objects.get_or_create(username="e2e-specialist", defaults={"system_role":"specialist"}); u.set_password(os.environ["DEMO_PASSWORD"]); u.save()'
```

Если Firefox на macOS не запускается из-за ограничений профиля, используйте официальный Linux-образ с той же версией Playwright. Из **корня** репозитория, при работающем E2E-стенде:

```sh
docker run --rm --init --ipc=host \
  --network container:alfa-credit-ui-e2e-frontend-1 \
  -v "$PWD/frontend:/work/frontend" -v "$PWD/.env:/work/.env:ro" \
  -v alfa-credit-ui-pw-node-modules:/work/frontend/node_modules \
  -w /work/frontend -e E2E_BASE_URL=http://127.0.0.1 \
  -e PLAYWRIGHT_HTML_OUTPUT_DIR=playwright-report-linux \
  mcr.microsoft.com/playwright:v1.64.1-noble \
  sh -c 'npm ci --no-audit --no-fund && npx playwright test --project=firefox --output=test-results-linux'
```

Linux-зависимости ставятся в отдельный Docker volume, не поверх macOS node_modules. Общий network namespace позволяет обращаться к Nginx как localhost, сохраняя допустимый Django Host и secure context для crypto.randomUUID. Результаты Linux имеют отдельные каталоги. Smoke-тесты AI=false не отправляют кредитную заявку, но входят в настоящий backend.

Финальная QA-регрессия: [актуальный отчёт](qa-product-research.md#независимая-итоговая-проверка-26102026). Для стенда без помощника задайте `AI_ENABLED=false VITE_AI_ASSISTANT_ENABLED=false` при Compose-сборке и `E2E_ASSISTANT_ENABLED=false` при тестировании: responsive-тест тогда проверяет отсутствие и кнопки, и панели. Перед браузерным прогоном дождитесь `--wait` и успешного `/api/v1/health/` через Nginx. Сохраняйте **все** QA-переменные портов и имени проекта при повторном `compose up`, иначе будут использованы порты из основного `.env`. Не меняйте production throttle ради серийных тестов; разделяйте группы/аккаунты и учитывайте Retry-After.

`jury-expiry.spec.ts` отдельно проверяет настоящие серверные сроки, без моков статуса. Он меняет только свежий синтетический Offer и требует явного `E2E_ISOLATED_COMPOSE_PROJECT=alfa-jury-qa-...`, Chromium, Docker CLI и совпадения `E2E_BASE_URL` с опубликованным frontend-портом этого проекта. Без opt-in тесты пропускаются; никогда не направляйте E2E на основную БД. Например, на отдельном стенде:

```sh
E2E_BASE_URL=http://127.0.0.1:18082 E2E_ASSISTANT_ENABLED=false \
  E2E_ISOLATED_COMPOSE_PROJECT=alfa-jury-qa-20261026 \
  npx playwright test tests/e2e/jury-expiry.spec.ts --project=chromium --trace=off
```

Пароль читается тестами из корневого `.env` либо окружения, не включён в JS. Служебные storageState лежат в игнорируемой `.auth/` с правами600, не коммитить их или traces: они могут содержать тестовые cookies. Тесты проверяют настоящий backend/PostgreSQL. Только ошибки потери ответа и недоступности сети воспроизводятся Playwright route fault injection; успешный кредитный процесс не подменяется моками.

## Ограничения и развитие

Все условия/оценки, подпись и выдача демонстрационные. Нет реальных БКИ/ФНС/платёжных интеграций, Grade A–E, банковского SLA, ручного переназначения деактивированного сотрудника или ИИ-сводки. Frontend не обходит эти ограничения. Поддержка HTTPS/публичного домена требует отдельной конфигурации и безопасных cookies.

Следующий продуктовый этап — **финансовый сценарий с прогнозом денежных потоков и стресс-тестами**. Он сохранён в roadmap, но исключён из текущих экранов, навигации и нумерации шагов.
