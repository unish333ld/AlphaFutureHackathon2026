## Исправления

| Дефект | Воспроизведение и исправление |
|---|---|
| После неверного пароля старое значение возвращалось в поле и мешало следующему входу | Регрессионный тест сначала падал на `toBeEmpty`. Неконтролируемый Core Input не синхронизировался с `setValue` React Hook Form. Оба поля переведены на Controller; пароль очищается, фокус возвращается в поле. |
| Сервер менял пароль, удаляя пробелы по краям | Три новых теста сначала падали. В DRF отключён `trim_whitespace` только для пароля: точное значение принимается, добавленные пробелы не игнорируются. |
| Запоздавший анонимный `/me` перекрывал успешный login диалогом истечения сессии | В тесте ответ 403 задерживается до успешного входа; до исправления модальное окно блокировало кабинет. Фоновые проверки при auth-переходе приостановлены, устаревшие результаты защищены поколением сессии. Сохранена защита от запоздавшего `/me` после logout и при уведомлениях другой вкладки. |
| Фоновый 503 убирал редактор и терял введённые данные | Тест сначала терял поле цели кредита. Теперь загруженные данные и экземпляры форм остаются при ошибке refetch, рядом показана ошибка с ручным обновлением. Это касается черновика и банковской карточки с вопросом уточнения. |
| Неуспешное обновление карточки возвращало cached data как будто это свежий ответ | `refresh` возвращает данные только при успешном GET. Подтверждение решения не открывается по устаревшим данным, POST не отправляется; после восстановления чтения действие снова доступно. Серверные права и lock_version по-прежнему проверяются повторно. |
| Кратковременная валидация пустого входа запускала минимальный период блокировки loading-кнопки | Spinner запускается только при фактическом сетевом входе; исправленный быстрый ввод и Enter после ошибок обязательных полей проверяются отдельно. |
| Кнопка видимости пароля внесла `svg-img-alt`-регрессию доступности | Smoke-тесты Chromium и WebKit отклонили SVG внутри стандартного PasswordInput. Использована композиция стандартных Core Input и текстовой Button с доступным именем/aria-pressed, без вмешательства в DOM библиотеки. Axe-проверка входа добавлена в основной E2E-сценарий. |
| Отложенные detail-запросы начинали fetch с уже отменённым сигналом | Два новых unit-теста сначала падали: пред-отменённый запрос передавался в fetch, пятый отменённый detail запускался после первых четырёх. Добавлен `throwIfAborted` до подготовки запроса и после ожидания CSRF; отменённые запросы не передаются в fetch. |

Добавлены доступные связи ошибок с полями (`aria-invalid`, `aria-describedby`), локализованное управление видимостью пароля, считывание нативных значений перед валидацией для менеджеров паролей без change-событий и защита от дублирования отправки. Session/CSRF, HttpOnly cookies и ограничение частоты входа сохранены. Пароли демонстрационных пользователей не сбрасывались. Модели, миграции и контракт OpenAPI в этом QA-цикле не изменялись.

Обычная вставка сама по себе в доступной среде не воспроизвелась как запрещённая: реальный Control+V успешно проверен в изолированном Linux Chromium, bulk-ввод — также отдельным сценарием. Системный буфер macOS пользователя не читался и не перезаписывался. Реальные Safari/iOS и конкретный браузер исходной жалобы не проверены; совпадение с причиной пользовательского случая без этих данных не утверждается.

## Границы проверки

Тесты используют настоящий Django/PostgreSQL backend. Только задержки ответов, 503, 429 и обрывы сети вводятся целевым Playwright fault injection. Успешный кредитный процесс не подменяется моками frontend.

Первый массовый браузерный прогон дополнительно выявил ошибку локатора нового теста (множественное вместо единственного числа в названии кнопки уточнения) и достижение настоящего лимита входов 429 при быстрых входах из одного IP. Локатор исправлен; лимиты безопасности не отключались. Окончательные прогоны выполняются по движкам с соблюдением окна ограничения.

Отдельная диагностика WebKit при принудительном `page.goto` с активными запросами показала сообщения access control: сначала 3/3 повторов не прошли, после защиты пред-отменённых запросов — 2/5. Эту проблему нельзя объявлять полностью исправленной нашим guard. У WebKit есть подтверждённая [ошибка классификации same-origin запросов при замене документа](https://github.com/microsoft/playwright/issues/43120). Обычный переход через продуктовую ссылку проверен отдельно; smoke теперь следует настоящей SPA-навигации пользователя. Проверка `pageerror` не фильтруется и не отключается. Принудительная замена документа с незавершёнными запросами остаётся известным ограничением этого WebKit-прогона, не доказательством ошибки CORS/CSRF на сервере.

Публичный HTTPS, реальные банковские интеграции, нагрузочное/полное security-тестирование и физические мобильные устройства не входят в этот прогон. Синтетические данные, проверки-моки, условная подпись/выдача и отключаемая демонстрационная ИИ-панель сохранены. Прогноз денежных потоков и стресс-тесты — следующий продуктовый этап, не часть текущего релиза. Успешный прогон означает отсутствие обнаруженных дефектов в перечисленных сценариях, а не доказательство отсутствия всех возможных багов.
