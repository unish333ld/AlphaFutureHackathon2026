## Изменения контракта 1.1.0

Отсутствие назначения подтвердилось в моделях/сервисах, не только в YAML. Добавлены Application.number/assigned_to/assigned_at/status_changed_at, самостоятельная staff-очередь, claim/release, история назначения, доступные действия с причинами. Банковские действия теперь требуют собственного назначения: frontend сначала выполняет claim. Клиентский список сохранён, клиентские действия не зависят от исполнителя. Реализованные ранее session/CSRF, решения серверной политикой, защита выдачи и изоляция компаний сохранены и повторно проверены; это не считалось отсутствующей функциональностью по одной схеме.

Новые миграции: applications.0002_assignment_and_queue и decisions.0002_assessment_checks_attempt. Initial-миграции не изменялись. Решение явно проверяет оценку текущей ревизии, полноту/актуальность попытки проверок и отсутствие missing/error. JSON factors/checks.result/input_snapshot/schedule/terms_snapshot/event.details типизирован в OpenAPI. Error соответствует фактическим DRF-формам; JSON login больше не отвечает HTML на CSRF-ошибку. OperationalError возвращается безопасным 503. Роль specialist не даёт выполнять клиентские действия даже при случайно добавленном company membership.

Релиз сохраняет синтетические данные/моки/условную подпись/выдачу. Не проверялись публичный HTTPS/Nginx/frontend, нагрузки и реальные банковские интеграции. SLA, Grade A–E, приоритизация и прогноз денежных потоков отсутствуют. ИИ остаётся только отключаемой визуальной заготовкой без backend LLM. Административного переназначения деактивированного исполнителя в двух ролях нет. Истечение в очереди отражает сохранённый статус до GET карточки/предложения либо expire_offers.

Этот отчёт фиксирует историческую backend-проверку. Последующее расширение необязательным помощником и актуальные результаты от 25.10.2026: [assistant-review.md](assistant-review.md). Настоящая модель в новом окружении не проверена.

## Найденный и исправленный дефект

`StrictSerializer.to_internal_value` возвращал ошибку неправильной формы для JSON-массива, строки или числа вместо объекта. На `POST /api/v1/applications/` это приводило к необработанному `ValueError` и HTTP 500 при чтении `serializer.errors`.

Ошибка теперь возвращается словарём с `non_field_errors`, и API отвечает 400. Регрессия проверяется реальными запросами с четырьмя типами некорректного JSON и отдельно для всех восьми входных сериализаторов. Изменения — в `backend/api/serializers.py`; проверки — в `test_api_contract.py`.
