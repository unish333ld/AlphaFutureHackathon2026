# PDF, демо-подтверждение и выдача

Актуальный контракт — [OpenAPI 1.3](openapi.yaml), не снимок 1.1 из навыка. Реальные SMS, телефон, криптографическая ЭП и денежный перевод не используются. ИИ не участвует. Требования этой задачи разрешают PDF и подтверждение поверх прежнего кредитного процесса.

## Пользовательский путь

1. Специалист берёт заявку и запускает решение по серверной политике. Клиент принимает одобрение или встречные условия.
2. Клиент с `can_sign` открывает «Подписать договор». Сервер формирует исходный PDF по принятому Offer/Agreement; повтор возвращает прежний документ. Доступны ссылки открытия/скачивания и необязательный встроенный просмотр. Без PDF-viewer остаются ссылки, паспорт и график на странице.
3. В «Просмотр договора» пользователь явно отмечает ознакомление и демонстрационный характер. Открытие/прокрутка PDF не считаются доказательством прочтения.
4. «Подписать договор» создаёт/восстанавливает допустимую серверную попытку и открывает «Подтверждение подписания». Через 1 секунду UI подставляет серверный демо-код и **один раз** отправляет существующий `sign`. Заполнение поля само по себе не устанавливает signed.
5. Закрытие до отправки убирает таймер и отменяет попытку. После отправки отмена не обещается. При потере ответа сначала читается договор; значимый запрос автоматически не повторяется.
6. Только серверный signed показывает «Договор подписан в демо-режиме» и постоянное ожидание выдачи. Копия с демо-отметкой создаётся отдельным запросом: ошибка копии не повторяет подпись, доступен отдельный повтор её формирования.
7. Назначенный специалист выполняет прежний `disburse` с lock_version и стабильным Idempotency-Key. Клиент выдачу не вызывает. При подтверждённом issued появляется отдельное сообщение «Демо-выдача завершена» с серверной суммой и пояснением об отсутствии перевода.

Сообщения результата закрываются примерно через 2,7 секунды или вручную; пользовательское взаимодействие/переход фокуса к контролам приостанавливает закрытие. Содержательный статус остаётся на странице. Нет повторной анимации при refetch/reload; `prefers-reduced-motion` отключает движения. В ожидании выдачи карточка перечитывается каждые 5 секунд; списки и действия обновляются по серверу.

## Хранение, версии и хеши

- `Agreement.document_hash` **сохраняет прежнюю семантику**: SHA-256 UTF-8 канонического JSON terms_snapshot (`sort_keys`, без лишних пробелов, `ensure_ascii=False`). Это не хеш PDF и не ЭП.
- `AgreementDocument`: исходный PDF либо отдельная signed_copy, версия 1; template_version `demo-credit-contract-1`, calculator_version `demo-annuity-monthly-v1`, снимок сторон/условий, источник Offer/revision, время начала формирования в snapshot.generated_at и время сохранения created_at, pdf_sha256, приватные binary-байты. PDF не содержит собственного байтового хеша: он отдаётся метаданными и `X-PDF-SHA256`.
- Байты хранятся в PostgreSQL, не в публичном media-каталоге. Повторное скачивание возвращает сохранённый артефакт; перерендеривания с новым временем нет. Ordinary save/delete исторических артефактов запрещены, в API нет произвольной правки. Это не WORM-хранилище против администратора БД; чтение и подпись проверяют целостность.
- UNIQUE(agreement, kind, version) и общая блокировка Application исключают два противоречащих активных документа. Подготовка снимка — короткая транзакция; WeasyPrint — вне неё; сохранение — повторная проверка прав, срока, источника и lock_version (CAS). Проигравшая генерация возвращает уже сохранённый документ либо 409, но не заменяет его.
- Стороны фиксируются для исходного документа. Новый договор дополнительно фиксирует company/product_name/purpose при принятии. Для старого договора используется его рассмотренная revision, а не изменившийся каталог/профиль компании; если старый снимок не содержит названия продукта, показывается сохранённый code. Старые terms_snapshot/document_hash не переписываются.
- Первый уполномоченный генератор фиксируется как демо-подписант этой версии. Произвольной смены подписанта готового документа нет. Реальная идентификация/доверенность не моделируются. ФИО, адрес, ОГРН, КПП, БИК и банковский счёт не выдумываются; обязательны сохранённые название/ИНН, продукт/цель и уполномоченная учётная запись. Отсутствие обязательного — 400; необязательное отмечено как не предоставленное.
- `SignatureConfirmation`: отдельная append-only запись с UUID события, договором, исходным документом, попыткой, user/company, временем, хешами и mode=demo_code. Событие signed ссылается на неё, без кода. Копия содержит эту отметку и SHA-256 исходного PDF. Исходные байты не изменяются.

Изменение финансовых условий требует нового разрешённого предложения и договора; новый живой каталог не меняет старые сделки. В этом релизе одна исходная версия на Agreement. У ранее подписанных договоров без кодовой попытки confirmation=null: UI честно не предлагает задним числом создать отметку кода.

## Код и защита

`SignatureAttempt` привязана к участнику, компании, договору, документу/pdf_sha256, document_hash и lock_version. Срок — 2 минуты, до пяти неверных проверок; до десяти новых попыток в час на участника и договор. Повтор begin с теми же актуальными данными возвращает pending; отменённая/истёкшая/locked/used не подтверждает операцию. Счётчики ошибок фиксируются даже при ответе 400. Два подтверждения сериализуются блокировкой заявки: одна подпись и одна аудиторская запись.

`DemoCodeAdapter` выдаёт шестизначный код только при `DEMO_MODE=true` **и** `DEMO_SIGNATURE_ENABLED=true`. Код возвращается браузеру — это намеренно **небезопасная для production симуляция**, не SMS, не второй фактор и не настоящая ЭП. В БД хранится digest, не открытый код; в аудит/логи код не включается. Адаптер выделен для будущей замены, настоящая доставка не реализована. Нельзя сделать production-подпись простым включением этого флага.

Sessions/HttpOnly/CSRF сохранены. Все операции используют company scope, действия требуют соответствующих полномочий. PDF доступен члену компании и специалисту через авторизованный endpoint. Ответ: application/pdf; inline либо attachment; private/no-store, Vary: Cookie, nosniff, SAMEORIGIN. UUID/имя файла не заменяют проверку доступа.

Входные строки экранирует Django Template, пользователь не задаёт HTML/CSS/ресурсы. URLFetcher разрешает только два точных локальных файла DejaVu; HTTP, data: и другие file: не разрешены. Вход — до 256 KiB, график — до 120 строк, PDF — до 4 MiB. Отдельный subprocess: 15 секунд wall-time, 12 секунд CPU, Linux address-space limit 768 MiB. Ошибка даёт безопасный 503 без stderr/реквизитов. Неизвестные комиссии/услуги не заменяются нулём: неполная модель не позволяет сформировать договор.

## API 1.3

| Запрос под `/api/v1/agreements/{id}/` | Назначение |
|---|---|
| POST generate-document/ | lock_version + document_hash → метаданные исходного PDF |
| GET pdf/?kind=original&download=true | те же сохранённые байты; без download — inline |
| POST signature-attempt/ | версия/оба хеша/document_id, acknowledged=true, confirm_simulation=true → attempt + demo_code |
| POST cancel-signature/ | attempt_id; USED не откатывается |
| POST sign/ | прежний endpoint, дополнен обязательными document_id/pdf_sha256/attempt_id/code |
| POST signed-document/ | отдельная копия после подписи; lock_version + document_hash |
| GET pdf/?kind=signed_copy | копия с демо-отметкой |
| POST disburse/ | прежний specialist + assignment + lock_version + UUID Idempotency-Key |

Agreement дополнен documents и nullable confirmation. Старые hash-only sign-запросы намеренно отклоняются (400): frontend обязан обновиться вместе с backend, обходного маршрута нет. Ошибки: 400 поля/код/неполные данные, 403 роль/CSRF, 404 чужой/несуществующий ресурс, 409 версия/состояние/целостность, 429 лимит, 503 рендерер. После sign/disburse перечитать карточку; при 409 сохранить ввод и проверить актуальную версию. Коллекция — [demo.http](demo.http).

## Оформление

Проверен [текст ГОСТ Р 7.0.97-2025](https://storage.consultant.ru/site20/202507/29/rosstandart_290725-gost.pdf): введён 18.08.2025 взамен 2016. Пункты 3.2/3.4/3.5 задают размещение нумерации, абзацев и выравнивания; 3.3 рекомендует размеры 12–14, допуская меньшие в таблицах; 6.1 задаёт минимальные поля. Выбрано шаблоном, а не «предписано банком»: A4, поля 30/15/20/20 мм, DejaVu Serif 12 pt, таблица 9 pt, интервал 1,2. Страницы со второй нумеруются сверху, заголовки таблицы повторяются, итог — только в конце. Кириллические шрифты встроены. Юридическая готовность договора из оформления не следует. Пользовательские PDF-референсы в текущем сообщении отсутствовали; сравнение именно с ними не заявляется.

## Запуск и проверочные образцы

Штатный путь — Docker Compose по README; дополнительные ручные установки Pango/шрифтов внутри контейнера не нужны. В Dockerfile закреплены Pango 1.56.3-1, HarfBuzz subset 10.2.0-1+deb13u1, DejaVu 2.37-8; WeasyPrint 70 и Python-зависимости — в requirements.lock. Для native Python нужны системные Pango/HarfBuzz и `PDF_FONT_DIR` с DejaVuSerif.ttf/DejaVuSerif-Bold.ttf; Docker предпочтительнее. После обновления: `docker compose up --build -d --wait --wait-timeout 180` с **прежним именем проекта/портами**, чтобы сохранить БД.

Миграция `agreements.0002_private_documents_and_demo_confirmation` только добавляет таблицы/ограничения, не подписывает старые договоры и не меняет их хеши. Перед обновлением существующего демо сделать backup PostgreSQL. Для проверок использовать отдельный Compose project и тестовую БД; не выполнять down -v для основной базы.

[Образцы](samples/) сформированы настоящим сервисом в изолированной тестовой БД: 1100000 ₽/24 мес. + копия, 300000,37 ₽/12 мес., 30000000 ₽/60 мес. Это не фиксированные runtime-шаблоны. Для визуального QA всех страниц: `pip install -r backend/requirements-test.lock`, затем `python scripts/render_contract_samples.py --input docs/samples --output .deps/pdf-qa-renders`. Результаты и оставшиеся ограничения — [qa-product-research.md](qa-product-research.md).
